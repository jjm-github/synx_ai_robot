# Synx AI Robot

Кросс-платформенное нативное приложение (Python + FastAPI + pywebview) для
производства в synx: отслеживание публикаций, AI-разбор комментариев,
постановка задач ботам, очередь выполнения и публикация версий.

Интерфейс — настоящее desktop-окно (pywebview), не вкладка браузера. FastAPI
работает локально на `127.0.0.1` и отдаёт только локальный UI.

## Установка

### Ubuntu / Linux Mint — скрипт

```bash
git clone <repo> synx_ai_robot
cd synx_ai_robot
./install.sh
```

Скрипт ставит системные пакеты (GTK/WebKit, `ffmpeg`, `arecord`), создаёт
`.venv`, ставит Python-зависимости, скачивает голосовые модели и создаёт
ярлык IIRobot. ComfyUI устанавливается отдельно — приложение подключается к
нему по URL.

Основные опции:

```bash
./install.sh --yes                  # без вопросов: voice-модели есть, LLM нет
./install.sh --llm small            # + qwen3.5:4b (~3.1 ГБ, меньше VRAM)
./install.sh --llm default          # + qwen2.5:7b (~4.4 ГБ)
./install.sh --llm both             # обе модели
./install.sh --llm custom --llm-models "qwen3.5:4b gemma4:12b"
./install.sh --no-voice-models      # без T-one/GigaAM (~450 МБ)
./install.sh --no-ollama            # не ставить Ollama
./install.sh --dry-run              # показать действия
```

Полный список: `./install.sh --help`.

### Ubuntu / Linux Mint — .deb

```bash
./packaging/build_deb.sh
sudo apt install ./dist/iirobot_1.0.0_amd64.deb
```

Пакет ставит приложение в `/opt/iirobot`, Python-wheels — в
`/opt/iirobot/wheels`, поэтому установка Python-зависимостей идёт без сети.
Данные и настройки пользователя лежат в `~/.local/share/iirobot` и
`~/.config/iirobot`. После установки:

```bash
iirobot-setup --voice-models --llm small
```

`.deb` собирается под Python текущей системы (Ubuntu 24.04 / Mint 22 — 3.12);
для другой версии Python собери пакет на целевой машине.

### Linux — один исполняемый файл

Вариант без установки пакета: PyInstaller складывает приложение, интерпретатор
и Python-зависимости в один ELF-бинарник.

```bash
.venv/bin/python -m pip install pyinstaller   # один раз
./packaging/build_bin.sh
./dist/iirobot
```

Результат — `dist/iirobot` (~60 МБ). `MODE=onedir ./packaging/build_bin.sh`
собирает каталог `dist/iirobot/`: стартует быстрее, но это уже не один файл.
Пересобирать нужно после каждого изменения кода; `build/` и `dist/` в
`.gitignore`.

Что важно знать:

- GTK/WebKit в бинарник **не** пакуются — окно рисуется системными
  библиотеками, поэтому нужны:
  `sudo apt install gir1.2-gtk-3.0 gir1.2-webkit2-4.1 ffmpeg alsa-utils`.
- Данные и настройки — в XDG-директориях, как у `.deb`:
  `~/.local/share/iirobot` (БД, планы, логи, `voice/models`) и
  `~/.config/iirobot` (`config.json`, `bots.json`, `system.md`,
  `mcp_servers.json`). Бинарник стартует с дефолтным конфигом; чтобы
  перенести текущий из репозитория:
  ```bash
  mkdir -p ~/.config/iirobot
  cp config.json bots.json ~/.config/iirobot/
  cp -r data/voice/models ~/.local/share/iirobot/voice/   # если нужен голос
  ```
- Не запускай бинарник одновременно с экземпляром из репозитория
  (`.venv/bin/python main.py`): у них разные БД и они будут спорить за одни
  и те же задачи.
- `./dist/iirobot --server-only` — только FastAPI без окна (порт печатается
  в stdout, свободный начиная с 8765).

### Windows 10/11 — PowerShell

```powershell
powershell -ExecutionPolicy Bypass -File .\install-windows.ps1
```

Скрипт работает без прав администратора: ставит Python 3.12 (winget или
официальный установщик), создаёт `.venv`, ставит зависимости из PyPI,
скачивает voice-модели, при необходимости ставит Ollama и LLM-модель,
создаёт ярлыки. Для Windows дополнительно ставится `sounddevice` (WASAPI),
а pywebview подтягивает `pythonnet` и использует Edge WebView2.

Опции:

```powershell
.\install-windows.ps1 -Llm small
.\install-windows.ps1 -Llm default -VoiceModels yes
.\install-windows.ps1 -Llm both -Ollama yes
.\install-windows.ps1 -NoShortcuts -SkipSystem
```

Настройки и данные: `%APPDATA%\IIRobot` и `%LOCALAPPDATA%\IIRobot`.
ffmpeg и poppler (PDF-инструменты) скрипт ставит/скачивает автоматически.

### Windows — установщик .exe

Сборка выполняется **на Windows x64** (Python 3.12 + Inno Setup 6):

```powershell
winget install -e --id JRSoftware.InnoSetup
powershell -ExecutionPolicy Bypass -File packaging\windows\build_windows.ps1
```

Результат: `dist\IIRobot-1.0.0-Setup.exe`. В установщике есть галочки
«голосовые модели» и выбор LLM (`qwen3.5:4b`, `qwen2.5:7b`, обе).
`build_windows.ps1` заранее скачивает Windows-wheels, Python 3.12 и
ffmpeg/poppler, поэтому Python-зависимости ставятся из локальных wheel-файлов.

### Ручная установка

```bash
python3 -m venv --system-site-packages .venv
.venv/bin/pip install -r requirements.txt
```

На Linux для pywebview нужен GTK/WebKit2 (`python3-gi`, `gir1.2-webkit2-4.1`
либо PyQt5). На Windows/macOS pywebview использует системный webview.

## Настройки

- `config.json` — AI провайдер, synx, ComfyUI, конвейер, системный промпт.
- `bots.json` — отдельный список ботов: логин, пароль, роль, вкл/выкл.
- `prompts/system.md` — системный промпт (редактируется и из UI).
- `data/robot.sqlite3` — SQLite: публикации, задачи, события.

По умолчанию synx: `https://synks.ru/`, пользователь `p.robot`.
Пароль и пароли ботов задаются в настройках приложения (`config.json`,
`bots.json`); в репозиторий они не попадают.

## Как работает

1. **Публикации** — сканирование synx (вручную или автоматически по
   `scan_interval_sec`), новые комментарии версий, задач и сущностей складываются
   в SQLite. Отдельный быстрый монитор событий (`event_interval_sec`, по
   умолчанию 30 с) читает `/api/events` и добавляет новые комментарии и
   сообщения с `@p.robot` в таблицу, не дожидаясь полного скана.
2. **AI-разбор** — выбранный комментарий (и вложения review-картинок)
   отправляется в OpenAI-совместимый провайдер. Модель возвращает JSON:
   название задачи, тип, бота, промпт, negative, workflow, references.
3. **Создание задачи** — через API synx создаётся задача, назначается бот.
4. **Конвейер** — задачи из очереди проходят этапы `analysis → generation →
   assembly → review → done`. Этапы, время и токены пишутся в SQLite; UI
   обновляет только активную строку каждые 5 секунд.
5. **ComfyUI** — если в задаче есть `workflow` или указан
   `comfy.workflow_path`, workflow отправляется в ComfyUI API. Поддерживаются
   плейсхолдеры `{{PROMPT}}`, `{{NEGATIVE}}`, `{{SEED}}`, `{{IMAGE}}`,
   `{{WIDTH}}`, `{{HEIGHT}}`, `{{FRAMES}}`, `{{SHOT}}`.
6. **Публикация** — при `auto_publish=true` версия публикуется от бота задачи.
   Иначе доступна кнопка «Опубликовать результат».

### Мониторинг событий и автообновление таблицы

- Полный скан — по `synx.scan_interval_sec` (по умолчанию 300 с).
- Быстрый монитор событий — по `synx.event_interval_sec` (по умолчанию 30 с),
  лимит событий `synx.event_limit` (200). Он вставляет новые комментарии,
  комментарии с `@p.robot` и обновляет флаги отвеченных.
- При следующем полном скане подтягиваются вложения и полный текст.
- Раздел «Публикации» удалён из интерфейса: приложение стартует сразу в чате.
  Сканирование и разметка продолжают работать в фоне, их состояние видно в
  статусбаре. Там же показаны основная AI-модель и модель коррекции речи
  вместе с устройством (CPU/GPU) и занятой VRAM.
- Новые `@p.robot`-сообщения учитываются сканером как приоритетные.

## Таблицы

Поведение таблиц повторяет synx_engine:

- ПКМ по заголовку — чекбоксы видимости колонок, сброс ширин, показать все.
- Перетаскивание правого края заголовка — ширина колонки.
- Ширины/видимость сохраняются в localStorage для каждой таблицы.
- Сортировка по клику на заголовок, фильтр по тексту.
- Мультивыбор строк чекбоксами.

## ПКМ по задаче

- открыть рабочую папку;
- пауза (текущая задача уступает следующей);
- продолжить;
- skip / unskip;
- опубликовать результат;
- удалить задачу;
- удалить задачу вместе с папкой;
- удалить все выполненные.

## Ограничения

- AI-провайдер должен поддерживать OpenAI-совместимый
  `POST /chat/completions` и (для review-картинок) vision-сообщения.
- Для реальной генерации нужен настроенный ComfyUI workflow. Без workflow
  задача завершится ошибкой на этапе generation — это сделано специально,
  чтобы не публиковать пустышки.
- `auto_publish` по умолчанию выключен: сначала проверяйте результат.
- Публикация выполняется от имени бота, назначенного на задачу; бот должен
  быть в `bots.json` и активен.


## ComfyUI

Приложение использует ComfyUI из `~/opt/ComfyUI` (пути можно изменить в
настройках). По умолчанию:

```text
base_url   http://127.0.0.1:8199
input_dir  ~/opt/ComfyUI/input
output_dir ~/opt/ComfyUI/output
```

Если ComfyUI запущен с другими `--input-directory/--output-directory`,
пропиши их в настройках.

Робот знает, где установлен ComfyUI, и умеет управлять сервером
(`comfy.root`, `comfy.base_url`):

- `comfyui_status` — путь установки, `main.py`, python, PID, лог, версия, GPU;
- `comfyui_start` — запуск сервера и ожидание ответа API;
- `comfyui_open` — запуск сервера и открытие интерфейса в браузере;
- `comfyui_stop` — остановка (только по явной просьбе);
- генерация и конвейер **сами поднимают сервер**, если он выключен.

Запуск: `/home/jaroslav/opt/ComfyUI/.venv/bin/python main.py --listen 127.0.0.1
--port 8199`, лог — `data/logs/comfyui.log`. Автозапуск и таймаут настраиваются
в `comfy.auto_start` и `comfy.start_timeout_sec`.

Робот также имеет доступ к shell и GUI этой машины:

- `run_shell` — выполнить команду (bash/cmd), вернуть stdout/stderr и код;
- `open_url` — открыть ссылку в браузере по умолчанию;
- `comfyui_open` — поднять ComfyUI и открыть его интерфейс.

Фразы «у меня нет доступа к shell/GUI» больше не являются корректным ответом:
этот доступ есть.

Встроенные workflow-билдеры:

- **FLUX.3 Klein i2v** — перерисовка/стилизация кадра по референсу;
- **FLUX.3 Klein t2i** — генерация кадра с нуля;
- **Wan 2.2 TI2V-5B i2v** — видео из первого кадра;
- **Wan 2.2 TI2V-5B t2v** — видео из текста.

Билдер выбирается по названию/промпту задачи: `wan/i2v/t2v/animate/video`
→ Wan 2.2, иначе FLUX.3. Любой из них можно переопределить полем
`workflow` в AI-плане или `comfy.workflow_path` в настройках.

## Шоты из сценария

`shot_script.py` + инструмент `create_shots_from_script` создают структуру шотов
строго по сценарию:

- имя шота — канонический ID из строки `s001_0010 · 200 кадров`;
- `display_name` = имя шота (`s001_0010`), чтобы в списке Entities были имена;
  тезис и диалоги — в `info`;
- `info` — код · план, ID · кадры, тезис и диалоги;
- `cut_out = cut_in + кадры - 1`, поэтому `length` точно равен длительности;
- на каждый шот создаётся одна задача **Conform** (`conform`) с ТЗ
  (длительность, сцена, что сдать) и назначенным ботом;
- версии **не** создаются;
- шоты линкуются к локации и к участвующим персонажам/объектам сцены
  (по именам персонажей и ключевым словам реквизита).

Повторный запуск идемпотентен: существующие шоты обновляются, дубликаты не
появляются.

## Сценарии по шотам

Сценарий эпизода — это не проза, а разбивка:

- каждая секвенция = одна локация: `## S01 · НАТ. ЛОКАЦИЯ — ВРЕМЯ`;
- внутри — шоты: `**S01-01 · WS · 8 c**`, ниже действие и реплики;
- у шота есть план (WS/MS/CU/OTS), действие и длительность;
- полный эпизод 8–12 минут, сумма длительностей сходится с хронометражем;
- в конце — правила и таблица хронометража.

Имена секвенций в synx — строго `s001`…`s014`; `display_name` совпадает с
именем. ТЗ секвенции пишется **сообщением в чат сущности** (`entity comments`,
инструмент `synx_entity_comment`): локация, тайминг, что происходит в эпизоде,
персонажи, графика, список шотов и задача. Поле `info` — только краткое
описание. Переименовывать секвенцию нельзя — `synx_update_entity` блокирует
смену её `display_name`.

Инструменты: `check_shot_script` (валидация структуры и хронометража) и
`publish_shot_script` (валидирует, собирает текстовый PDF, публикует версию и
прикладывает `.md` + PDF публикацией к задаче). Прозаический синопсис
валидатор не пропускает.

## Текстовые документы

Сценарии, планы и `.md` публикуются как **векторный текстовый PDF**: настоящий
выделяемый текст, белый фон, встроенные DejaVu-шрифты (reportlab). Страницы не
рендерятся в картинки — `pdftotext` извлекает текст, `pdffonts` видит шрифты.

- `make_text_pdf` — markdown/текст → текстовый PDF (A4/A3/LETTER, размер шрифта);
- `publish_text_document` — собрать, проверить и опубликовать версией под задачей;
- `synx_attach_files` — приложить `.md`/`.txt`/`.json` публикацией к задаче
  (`target=task`). Комментарии synx принимают только картинки, поэтому
  текстовые файлы идут публикацией p001, p002… и видны в задаче. Повторная
  публикация того же файла пропускается (сравнение по SHA-256).
- `synx_set_task_status` — смена статуса задачи (todo/wip/Pending_Review/done/hold/omit).
- `synx_entities` — список сущностей проекта (id, имя, display_name, тип, created_by,
  число версий/задач) — для поиска и чистки.
- `publish_pdf_as_version` — опубликовать готовый PDF версией для ЛЮБОЙ сущности
  (локация, объект, персонаж, шот). `publish_images_as_version` работает только
  для шотов; для ассетов — этот инструмент.
- `synx_assign_task` — назначить бота на существующую задачу по логину.
- `synx_update_entity` — обновить `info` (ТЗ), `display_name`, `asset_type`.
- `synx_task_comment` — добавить комментарий/ТЗ к задаче.

## Именование сущностей и ТЗ

- `name` сущности — латинский slug, совпадающий с папкой: `loc_...`, `obj_...`,
  `p002_0130`. Кириллица в именах и папках не используется.
- `display_name` — человекочитаемое название (латиница/английский).
- `info` — полное ТЗ на русском: что это, геометрия, свет, материалы, цвет,
  что в кадре, зачем. Пустое ТЗ недопустимо.
- Имя задачи — slug, совпадающий с папкой/сущностью (например
  `loc_ocean_seiner`), а не тип (`art`). В первом комментарии задачи — ТЗ:
  задача, исходные данные, формат сдачи, стиль, что сдать, критерии приёмки.
  Заглушки вида «Art task for ...» недопустимы.
- При создании сущности задачи создаются явно с именем сущности; авто-задачи
  вида `art` больше не появляются.

## Голосовой ввод (локально)

Удерживай кнопку **«🎤 Держать»** в чате: пока говоришь, в поле ввода идёт
черновой текст; отпустил — движок перечитывает фразу и выдаёт чистовой вариант.

- **Поток**: T-one streaming CTC (8 кГц, русский) — частичный текст почти сразу.
- **Финал**: GigaAM v3 e2e CTC (16 кГц, пунктуация) — точный текст по всей фразе.
- **Правка**: LLM добавляет пунктуацию/регистр и чинит термины (шот, ассет, synx…).
- **Корректор по умолчанию — локальный Ollama на GPU** (`qwen2.5:7b-instruct-q4_K_M`):
  ~0,5–1,5 с на фразу, модель полностью в VRAM. Облачный AI больше не участвует
  в голосовом вводе, поэтому нет сетевой задержки. Модель прогревается в фоне,
  пока идёт запись, — холодный старт не ждёт пользователь.
- Все настройки — **Настройки → Голос**: вкл/выкл коррекции, провайдер
  (**локальная модель Ollama / основная модель AI-провайдера / без коррекции**),
  URL и модель Ollama, `keep_alive`, таймаут. При выборе «Основная модель»
  коррекция идёт через ту же AI-модель, что и чат; для reasoning-моделей
  размышления на время коррекции отключаются, чтобы не тратить токены впустую.
  Кнопка **«Проверить корректор»** показывает время, модель и объём VRAM.
- Модель выбирается из списка установленных в Ollama (с размером на диске и
  текущим VRAM) либо вводится вручную. Кнопки **«Обновить»** и
  **«Выгрузить из VRAM»** позволяют освободить видеопамять; при смене модели
  старая выгружается автоматически.
- ASR работает на CPU: T-one ~144 МБ, GigaAM ~320 МБ; видеокарту занимает
  только текстовый корректор (~4,9 ГБ VRAM у 7B Q4).
- Модели прогреваются фоново при старте приложения (и при включении галочки):
  первое нажатие не теряет первые секунды речи. Если нажать во время прогрева,
  звук буферизуется и досылается в распознаватель, как только модель готова.
- Галочка **«голос»** выключает ввод и выгружает модели распознавания и
  локальный корректор из памяти (включая VRAM).
- Кнопка: **«Нажмите»** → при удержании **«Говорите»** (синяя) → после отпускания
  **«Думаю...»** (жёлтая, мигает, точки 1→5→1) → снова «Нажмите».
- Микрофон: `arecord` (16 кГц mono); устройство можно задать в `voice.audio_device`.
- API: `/api/voice/status|start|partial|stop|toggle|transcribe|correct/test`.

## Масштаб интерфейса

**Ctrl + колесо мыши** (или Ctrl + `+` / `-` / `0`) меняет масштаб всего
интерфейса, включая шрифт: от 70% до 160%, шаг 5%. Масштаб сохраняется в
`localStorage` и применяется при следующем запуске. В PDF/картинка-вьювере
Ctrl+колесо оставлено для зума самого документа.

## Токены по шагам

Во время ответа каждая строка «Думаю…» в блоке размышлений показывает справа
входные и выходные токены именно этого шага: `вход 22 475 · выход 5`. Итоговые
токены ответа по-прежнему показываются под сообщением.

## Сплиттер истории и ввода

Между историей чата и областью ввода есть горизонтальный сплиттер. Потяни его
мышкой вверх/вниз — высота истории и поля ввода меняется. Двойной клик
сбрасывает размер по умолчанию. Высота сохраняется на сервере
(`data/ui_chat_panels.json`) и восстанавливается при следующем запуске.

## Чат: выделение, drag и вставка файлов

- ПКМ по выделенному тексту → **«Вставить в запрос»** (и «как цитату»): текст
  попадает в поле ввода, курсор ставится после вставки.
- Файлы из другого приложения можно **перетащить** прямо в поле ввода — они
  прикрепятся как референсы. Поддерживаются изображения, PDF, видео, `.md`,
  `.json`, таблицы и любые другие файлы; не-изображения показываются карточкой
  с именем и размером и открываются по клику.
- Выделенный текст можно **перетащить** в поле ввода: во время drag показывается
  каретка и подпись «вставить здесь» — точно в месте будущей вставки, даже если
  поле не пустое.
- **Ctrl+V с картинкой** работает, когда мышь над окном чата, даже если фокус не
  в поле ввода: изображение загружается и появляется чипом вложения.

## Obsidian: карта ассетов

`obsidian_export.py` + инструмент `export_obsidian_map` выгружают проект в
Obsidian-секцию (по умолчанию `TEST_PROJ` в vault из `paths.obsidian_vault`):

- каждый ассет — отдельная статья (`Locations/`, `Models/`, `Characters/`,
  `Script/`, `Shots/`) с ТЗ, связями, задачами и версиями;
- связи — wikilinks на связанные ассеты, поэтому граф Obsidian показывает карту;
- `TEST_PROJ.md` — map-нота: локации с объектами и персонажами;
- `Карта ассетов.canvas` — визуальная JSON Canvas карта связей.

## Задачи из чата — через конвейер

Любая производственная работа из чата (генерация, серия кадров, задачи на
локации/объекты) ставится в конвейер инструментом `queue_generation_tasks`:

- создаётся видимая задача в разделе «Задачи» (status/progress/stage);
- `entities=["all_locations"]` — задачи на все локации проекта;
- промпт с `{entity}` подставляется для каждой сущности;
- после постановки робот сообщает: сколько задач, их ID, проект, сущности и где
  смотреть. Без лишних вопросов.

Одиночный быстрый предпросмотр можно генерировать инлайн; серии и пакеты — только
через очередь, чтобы было видно, где что считается.

## Паспорта локаций (9 видов + превью)

`passport_batch.py` + инструмент `start_passport_batch` собирают паспорт локации
из **10 страниц A3**: страница 1 — контактный лист (превью 3×3), страницы 2–10 —
9 разных видов (общий, обратный, нижний, аэро, деталь, интерьер, подход, свет,
настроение). Каждый вид генерируется отдельно (FLUX.3, 1536×864), затем PDF
публикуется новой версией Concept/location_develop.

Запуск из чата: «по 9 видов + 1 превью для всех локаций». Батч работает в фоне
(~3 минуты на локацию), статус — `data/passport_batch.json`, лог —
`data/logs/passport_batch.log`.

## Связи ассетов

`EntityCreate` игнорирует `linked_asset_ids` (и `task_types`) — связи нужно
записывать отдельно через `PATCH /api/entities/{id}`. Инструмент
`synx_link_assets` делает это и по умолчанию пишет связь в обе стороны:

- каждая локация → все её объекты и персонажи;
- каждый объект/персонаж → все его локации;
- объект, который встречается в нескольких локациях, линкуется ко всем.

Проверка: `linked_assets` не пуст у каждого объекта/персонажа, а у локации —
все её объекты и персонажи.

Для шотов есть отдельный массовый инструмент `synx_link_shot_assets`:
карта `{шот: [ассеты]}` за один вызов записывает `linked_asset_ids` и
дописывает в `info` блок `СВЯЗАННЫЕ АССЕТЫ: локация — …; персонажи — …;
предметы — …`. Связываются только видимые в кадре ассеты; голос за кадром не
считается. `synx_shots` с `with_info=true` даёт шоты и их ТЗ для разбора.
Инструмент идемпотентен и не плодит блоки при повторном запуске.

Только по явной просьбе; сущности с версиями/задачами удаляются лишь с
`force=true` после подтверждения.

Чёрный фон остаётся только у daily-PDF с кадрами; для текста он не используется.
Проверка: `pdftotext` извлекает текст, `pdffonts` показывает встроенные шрифты.

## Структура рабочих файлов

Все рабочие файлы генерации — PNG/JPG, видео, workflow JSON, PDF, meta,
README — лежат под задачей, в папке бота, назначенного на задачу:

```text
<projects_root>/<project>/shots/<sequence>/<shot>/<task_type>/work/<bot>/<task_name>_vXXX/
```

Для asset-сущностей:

```text
<projects_root>/<project>/assets/<asset>/<task_type>/work/<bot>/<task_name>_vXXX/
```

Финальные рендеры (PNG/MP4/PDF и отдельные файлы):

```text
<shot_dir>/render/vXXX/
```

Нельзя складывать рабочие файлы в корень проекта, `render/` без `vXXX` или
произвольные папки. Превью в `data/chat` — временное; канонические файлы
задачи — только в папке задачи/бота.

Шаблоны путей настраиваются в `config.json` → `paths.layouts`.


## Чат

Приложение стартует сразу в чате: вкладки «Публикации» больше нет. Можно:

- задавать вопросы по производству и synx;
- прикреплять референсы любого типа: кнопка «+ Референс», перетаскивание
  файла из другого приложения в поле ввода или вставка из буфера;
- просить сгенерировать изображение: «нарисуй … по этим референсам»;
- получать картинку прямо в чате.

Генерация идёт через ComfyUI: FLUX.3 i2v при наличии референсов, иначе t2i.
Модель может вызвать `generate_image` или `generate_from_synx_version`; если
провайдер не поддерживает tool calling, работает fallback по ключевым словам.

### Инструменты и лимит шагов

Чат не отключает инструменты: у него есть бюджет шагов на один ответ
(`ai.max_tool_steps`, по умолчанию 100). При исчерпании бюджета робот
формулирует итог по уже выполненным вызовам и не утверждает, что инструменты
выключены. Для массовых операций есть `create_tasks_for_all_shots` — одна
задача на каждый шот за один вызов, без поштучного цикла.

### Генерация из версии synx

Запрос вида «найди в проекте colossus версию p002_0130 v004, загрузи её как
референс и сгенерируй картинку в стиле кубизм с сохранением композиции и
пропорций» обрабатывается одним проходом:

1. `synx_find_version` ищет шот и версию; если в указанном проекте шота нет,
   поиск автоматически идёт по остальным проектам (с пометкой
   `project_corrected`);
2. версия скачивается в `data/refs/versions/<project>/`;
3. для видео извлекается средний кадр, для изображения берётся исходник;
4. размер генерации считается по пропорциям исходника (с ограничением по
   стороне/мегапикселям), затем результат аккуратно кадрируется до точного
   aspect ratio исходной картинки;
5. FLUX.3 i2v собирается с `workflow_config`: `profile`, `steps`, `cfg`,
   `denoise`, `megapixels`, `preserve_aspect`, `style`, `models`
   (`unet`/`clip`/`vae`).

Тот же `workflow_config` можно вернуть в AI-плане задачи — конвейер применит
его в `build_for_task`, не меняя остальные задачи.

Ссылки в чате и планах открываются во внешнем браузере, а не внутри окна
робота. Локальные пути файлов (PDF/PNG/видео) кликабельны и открываются в
системном просмотрщике.

Просмотр изображения:

- колесо — зум к курсору;
- средняя кнопка + движение — панорама;
- средний клик — сброс зума;
- ПКМ — «Сохранить как...» и «Копировать изображение».


### PDF из кадров и публикация версии

Робот умеет склеивать отдельные картинки в многостраничный PDF — по одной
картинке на страницу — и публиковать его как версию:

- `make_pdf_from_images` — собрать PDF из последних картинок чата или явных путей;
- `publish_images_as_version` — собрать PDF, создать задачу в synx (по умолчанию
  `Art`), выбрать и назначить бота по скилам из synx API, разложить PNG и
  workflow JSON в рабочую папку задачи и в `render/vXXX` шота, затем
  опубликовать PDF от имени бота.

Пример: 5 кадров → PDF на 5 страниц (2062×864), задача `cubism_frames`, бот
`e.matveev` (Render, AI), версия `v005` в Liberia / p002_0130.

### Daily PDF

Отдельный базовый layout для дэйли (контактный лист + карточки кадров):

- страница 1 — все кадры мелко;
- далее по одному кадру на страницу, фон чёрный, кадр по ширине листа
  (боковые края совпадают с границами);
- под кадром серым текстом (белый ~50%): Prompt EN/RU, модели и LoRA,
  время генерации, PC/GPU/VRAM/CPU/RAM/SWAP, стоимость API, длина видео,
  разрешение;
- те же данные попадают в комментарий публикуемой версии;
- PDF проверяется: число страниц, A4 842×595 pt, пустые страницы.
- 300 dpi поддерживается (страницы остаются A4 по точкам, картинка рендерится
  с 300 dpi).
- PDF-просмотр в роботе: `pdf_render_pages` параллельно рендерит все страницы
  в кэш PNG (`data/pdf_cache/...`), а встроенный viewer показывает уже готовые
  страницы с зумом/панорамой, не дожидаясь полной загрузки PDF.
- Пересборка по базовой версии: если пользователь говорит «версия 13,
  исправь…», робот берёт кадры задачи и вызывает `publish_daily_pdf` с
  `base_version`, `dpi`, `text_scale`, `image_valign`, `background`, не
  генерируя изображения заново.

Инструмент: `publish_daily_pdf` (или `daily_pdf.make_daily_pdf` +
`publish_flow.publish_daily_pdf`). Пример: v013 в Liberia / p002_0130 —
6 страниц, чёрный фон, подписи и железо.

### ffmpeg и MCP

`ffmpeg`/`ffprobe` установлены и являются базовыми инструментами: нарезка,
склейка, кадры, слайдшоу, проверка видео — прямыми вызовами. MCP-серверы можно искать/устанавливать/редактировать в приложении, а включённые
серверы вызываются из чата через `mcp_list_tools` / `mcp_call`.

Для ComfyUI включён **`artokun/comfyui-mcp`** — 41 инструмент:
`create_workflow` (create/modify/validate), `download_model` (HuggingFace/CivitAI,
checkpoints/loras/vae), `list_local_models`, `search_custom_nodes`,
`install_custom_node`, `get_workflow`, `save_workflow`, `visualize_workflow`.
Для видео — `ffmpeg-skill` MCP (`probe`, `cut`, `fit`, `caption`, `graphics`).
Для PDF проще прямой PIL-пайплайн.

Для веб-поиска включён **`ddg-search`** (DuckDuckGo MCP):
`web_search(query)` и `web_fetch(url)` в чате.

Веб-исследование работает автоматически: если в запросе есть «поищи / найди в
интернете / погугли» или это технический вопрос про ComfyUI, LoRA, ноды, модели,
ошибки и решения воркфлоу, робот без дополнительных напоминаний:

1. формулирует 1–2 коротких поисковых запроса;
2. ищет через DuckDuckGo;
3. читает 1–2 самые релевантные страницы (`fetch_content`, при ошибке — прямой
   HTTP-запрос с очисткой HTML);
4. отвечает шагами со ссылками и честно говорит, если факта в источниках нет.

Отдельный тул-луп больше не упирается в «Слишком много шагов»: при исчерпании
шагов или повторах вызовов робот формулирует ответ по уже собранным данным.

Альтернативы ComfyUI MCP: официальный `Comfy-Org/comfy-mcp` (локальный контроль,
download по URL) и `ConstantineB6/comfy-pilot` (редактирование live-графа).

Робот также умеет создавать сущности и задачи через synx API:
`synx_create_entity` (asset/shot, с автоподбором кода `asset_type` по label),
`synx_create_task` (с назначением бота) и `synx_asset_types`/`synx_task_types`
для проверки допустимых типов. Пример: ассет `main_script` типа `Script` в
`test_proekt_vfx` с описанием «разработка главного сценария фильма».

## Фокус чата и защита от лишних публикаций

- Робот запоминает project/shot/version из текущего сообщения (таблица
  `chat_focus`) и показывает их модели как «Текущий фокус».
- История чата короткая (16 сообщений), а при явной смене шота/версии старые
  сообщения отрезаются — древние версии и прошлые PDF-эксперименты больше не
  всплывают в новом запросе.
- Публикация разрешена по явной команде («опубликуй», «сделай версию»,
  «запушь», «сделай публикацию»). Разрешение действует всю сессию: «продолжай»
  после него публикует без переспросов. «Не публикуй» снимает разрешение.
- Фокус переключается текстом в чате: «в test_proekt_vfx / main_script»,
  «фокус: <проект>/<сущность>», «шот p002_0130», русские названия проектов
  («тестовый проект», «либерия»). Переключать что-то в интерфейсе не нужно.
- Если инструмент пытается опубликовать цель, которую пользователь не называл
  в последних сообщениях, публикация блокируется (`focus_mismatch`); цель,
  названная пользователем, подхватывается автоматически.
- Массовые публикации: несколько документов = несколько версий за один заход,
  без переспросов; опыт этого описан в системном промпте робота.
- Запрос «возьми версию X за основу и собери воркфлоу» обрабатывается
  детерминированно: находится именно эта версия, скачивается референс-кадр,
  ничего не публикуется; при выключенном ComfyUI робот честно об этом пишет.
- Правки PDF («чёрные листы», «текст мельче», «кадр по центру», 300 dpi)
  распознаются и без слова «pdf», поэтому не уходят в тул-луп.

## Synx API для робота

Актуальный справочник API лежит в `prompts/synx_api.md` и подмешивается в
системный промпт чата: проекты, сущности, задачи, версии, комментарии,
события, личные сообщения, task_types, assignments-form (скилы ботов),
публикации задачи, публикация версии, media kinds и формат плейлиста.

Важно для PDF: после публикации робот проверяет `media.kind`. Если synx
вернул `null`, PDF не распознан для этой сущности/типа задачи — плеер может
показать пустоту; нужен preview (контактный лист/слайдшоу) или PDF-friendly
задача/asset. Сам PDF при этом проверяется по страницам и размеру.

## Synx-инструменты в чате

Чат использует данные Synx из настроек (`base_url`, логин, пароль) и умеет:

- `synx_projects` — список проектов;
- `synx_find_version` — точный поиск версии по project + shot + version;
- `synx_versions` — версии проекта за период (можно фильтровать по shot/version);
- `synx_tasks` — задачи проекта;
- `synx_make_playlist` — плейлист Synx Player за период;
- `generate_from_synx_version` — скачать версию, взять кадр и сгенерировать
  изображение одним вызовом;
- `synx_project_news` — сводка по локальной таблице за период;
- `synx_bots` — настроенные боты, их скилы и доступность в synx;
- `make_pdf_from_images` — склейка картинок в PDF;
- `publish_images_as_version` — PDF + задача + бот + раскладка файлов + версия.

Плейлист формируется по формату `synx_engine`:

```text
<start synx playlist:
{"synx_playlist": 1, "items": [...]}
end synx playlist>
```

В чате он показывается карточкой с кнопкой **«Скопировать»**. Текст можно
вставить в плейлист Synx в браузере (Ctrl+V).

### Сводка «что нового»

Если спросить «что нового в проекте … за …», робот сначала вызывает
`synx_project_news` — читает уже собранную локальную таблицу, сравнивает с
последним просмотром этого чата (`project_views.last_seen_id`) и отдаёт:

- сколько новых сообщений с прошлого просмотра (`first_view` для первого раза);
- продолжения, отвеченные, версии и упоминания `@p.robot`;
- топ шотов по активности (ближайший фронт работ);
- список действий, упоминаний и последних версий;
- текстовый digest, по которому модель делает краткое резюме.

## Сессии чата

История чата хранится в SQLite и переживает перезапуск приложения. Каждая
сессия имеет свой контекст; сессии можно создавать и переключать в верхней
панели чата. Модель при каждом запросе получает историю текущей сессии.
Пока один чат думает, можно переключиться на другой и отправить там запрос —
задачи выполняются параллельно, а при возврате в первый чат его прогресс
продолжает отображаться. Escape не останавливает размышления; остановка —
только кнопкой «■ Стоп».


## Темы

Кнопка **◐** в верхней панели открывает меню тем из synx_engine:

- Redmond;
- Ash;
- Dark;
- cs 1.6;
- своя тема.

Пункт **«Редактор тем…»** открывает диалог с загрузкой картинки-источника,
ручным выбором цветов, кнопкой **Sample!** (сэмплирование четырёх цветов
с картинки), предпросмотром, сохранением/загрузкой `.json` и применением.
Тема сохраняется на сервере (`data/ui_theme.json`) после каждого изменения и
встраивается в страницу при следующем запуске, поэтому переживает перезапуск
даже в WebKitGTK без `localStorage`.


## Разметка публикаций

При сканировании новые комментарии автоматически отправляются AI-разметке
(`synx.auto_analyze`). Для каждого определяется:

- **продолжение** — нужна новая версия/генерация/исправление;
- **версия** — публикация версии, уведомление или положительный отзыв.

Если после комментария по тому же шоту уже выпущена версия (для комментариев
задачи — версия этой же задачи), комментарий считается **отвеченным версией**.
Такой комментарий не требует продолжения, задача по нему не предлагается и не
создаётся. При сканировании флаги отвеченных комментариев обновляются
автоматически, повторный ручной разбор не нужен.

Раздел «Публикации» и его таблица удалены из интерфейса. Разметка осталась
внутренним этапом сканирования: результаты хранятся в SQLite и используются
конвейером, но отдельной вкладки и REST-эндпоинтов `/api/publications*` больше
нет.

### Приоритетные сообщения @p.robot

Сканер ищет упоминания `@p.robot` в комментариях версий, задачах,
комментариях сущностей и в свежей ленте событий synx. Такие сообщения
считаются приоритетными указаниями:

- помечаются в таблице бейджем **`@p.robot`** и фильтром
  «упоминания @p.robot»;
- всегда классифицируются как «с продолжением», даже если в тексте нет
  обычных слов-триггеров;
- автоматически ставятся в AI-разбор, который формирует конкретное
  руководство к действию (summary/prompt) на основе текста сообщения;
- задачи из таких сообщений получают приоритет и запускаются конвейером
  раньше обычных;
- если по сообщению уже выпущена версия, оно считается отвеченным и задача
  не создаётся.

## Ссылки на версии в задачах

После публикации версии задача получает ссылку вида:

```text
https://synks.ru/p/colossus?tab=tasks&t=shot-c004_0020-prod_gen-ink_watercolor&v=shot-c004_0020-v003
```

Она открывает проект Synx с выбранной задачей/шотом и версией в плеере.
Ссылка открывается во внешнем браузере через pywebview bridge.
